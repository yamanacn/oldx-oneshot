# 第一阶段：配音（用用户自己的声音）

把用户给的文案，用用户自己的声音念出来，并留下后续环节（分段、数字人）要用的逐词时间。参数已固定，流程只有一条路，目标是让用户少说话、少操作。

固定的东西都在 `scripts/voice/common.py` 里：合成模型 `qwen-audio-3.1-tts-flash`、默认指令（"像朋友聊天一样自然随意的口语，不要播音腔，语速较快，句与句之间保留自然的停顿，语气轻松带笑意"）、48k wav、每段最多 1000 字、最多 6 路并发；识别模型 `qwen-audio-3.1-asr-flash`。这些是用户在试听对比后定下的，所以不要向用户提问或推荐别的音色、模型。**语速用"较快"**；情绪靠两样东西控制：开头的整体描述，和句首的情绪标签（第 4 步）。

全程只用百炼一个服务、一个 Key：合成、复刻、识别都是它，不需要在本机安装任何识别工具。

## 项目目录（文案缓存）

每份文案对应一个项目目录，默认 `~/.digital-human/projects/<日期-哈希前8位>/`（Windows 为 `%USERPROFILE%\.digital-human\projects\...`，可用环境变量 `DH_WORKSPACE` 改根目录）。下文称 `workdir`。里面有：

- `copy.txt`：用户文案原文（一个字不改）；`meta.json`：哈希、字数，以及各环节写回的进度
- `voice.json`、`paragraphs.json`、`cache/`、`out/`（配音、`timeline.json`、`words.json`）

文案去掉空白后哈希相同就算同一份：直接命中缓存、复用已有音频和逐词时间，不重复合成。数字人、包装两个阶段读同一个目录（约定见 `references/pipeline.md`）。用户的默认音色记在根目录的 `voice.json`，新项目不给样本就复用它。

## 红线

- **密钥不回显。** 任何输出、命令、文件说明里都不要出现密钥原文，只说"找到了，来源是……"。
- **不从聊天记录、日志、settings 里翻密钥。** 本机没有就问用户；翻记录等于绕开用户，这是被明确禁止的做法。
- **不改文案。** 文案是用户的，不润色、不增删、不纠错字；发现可疑的地方只在最后提示，由用户决定。
- 其余（是否本人声音、噪声、费用）按用户的要求不询问、不提示，直接做。

## 流程

脚本路径相对本技能目录。

### 0. 查 Key

```
python scripts/voice/check_key.py
```

- 退出码 0：找到了，继续。只告诉用户来源。
- 退出码 3：本机没有。把下面这段话**原样**发给用户，然后**停下等待**，不做任何别的事：

  > 本机没有注册百炼的APIkey。请获取apikey后，直接粘贴到对话输入框发送给我，其余的我来处理。
  > 获取地址：https://bailian.console.aliyun.com/cn-beijing/model/settings/api-key

  需要补充说明时再看 `references/voice/onboarding.md`（新用户怎么开通、怎么复制 Key）。**用户只需要粘贴，不要让用户打开终端、设置环境变量或运行任何命令**，所有命令都由你来执行。

- 用户把 Key 发来后，**直接保存并告知**，不再追问：用 Write 工具把 Key 原文写入 `~/.bailian/api_key`（Windows 为 `%USERPROFILE%\.bailian\api_key`，不要有多余换行或说明文字），再运行 `python scripts/voice/check_key.py --lock` 限制为仅当前用户可读。然后只说一句："已收到并保存在本机（仅你的账户可读），之后不用再发；想删除告诉我。"不复述 Key 的内容。保存之后的运行都从文件读取，不必再用环境变量。

### 1. 收文案，先缓存

1. 拿到用户的文案（文本或文件）。贴在聊天里的，用 Write 工具原样存成一个临时文件（UTF-8）。
2. 建立或命中项目缓存：

   ```
   python scripts/voice/project.py init --copy <文案文件>
   ```

   输出里有 `project_dir`（后面的 `workdir`）、`cache_hit` 和各环节进度 `state`。**如果 `state.audio` 和 `state.words` 都已有**：告诉用户命中缓存、直接复用，跳到第 6 步交付；用户明确要重做才继续。

3. 人声样本：用户给一段 10–20 秒、干净、无背景音的正常口播（wav/mp3/m4a；接口范围 5–60 秒，10 秒和 35 秒的都用过）。如果已经有默认音色（上次复刻过），就不用再要，告诉用户"沿用你上次的声音"，用户说要换再要样本。

### 2. 复刻音色

```
python scripts/voice/clone_voice.py --workdir <workdir> --sample <样本>
python scripts/voice/clone_voice.py --workdir <workdir>                    # 沿用默认音色
python scripts/voice/clone_voice.py --workdir <workdir> --sample <新样本> --force   # 换声音
python scripts/voice/clone_voice.py --list                                 # 复刻过的所有音色
python scripts/voice/clone_voice.py --workdir <workdir> --use 1            # 换回以前的某个音色，不用重新上传
```

用户说"还是用上次那个声音""换回 X 月 X 日的"时用 `--list` 找，再 `--use`，不要让用户重新给样本。每次复刻都会把默认音色改成最新的，换回来时 `--use` 会一并改回。

直接上传复刻，不问授权、不检查噪声。样本短于 5 秒时脚本会报错（接口会拒绝），让用户重新给一段；其他情况不拦。

### 3. 通读全文，按大段拆分

先把整篇文案从头读一遍，理解它的结构，再拆。目的是让每一段的情绪稳定，所以：

- **用户的换行就是用户要的分段，按他的分。** 用户贴来的文案已经分好段，就一段一段用，不要再自己合并或打碎；只有某一段超过上限才在它内部再拆。（实际发生过：自己拆成十几小段，用户嫌太碎。）
- **用户没分段时，按话题转折拆成 5–8 个大段，每段 250–500 字，不按句子拆。** 拆得越碎，各段接缝处的语气越容易不连贯，宁可少拆。
- **每段最多 1000 字**（整篇 1551 字一次合成成功过；488、501 字的段也稳）；全文不超过 1000 字就整篇一段，不必拆。
- 分段越少，各段语气越一致；分段越多，越方便只重做某一段。各段的语速、音高在核对里会列出来。
- 拆在自然的换气处：话题切换、"第一步/第二步"之间、总起和展开之间；不要在一句话中间断开。
- 一段很短（几十字）时并入相邻段，除非它本身就是独立的开场或结尾。
- 不改字：各段拼起来必须等于原文（空白除外）。

把结果写成 `<workdir>/paragraphs.json`：`{"paragraphs": ["第一段……", "第二段……"]}`，然后把关：

```
python scripts/voice/split_check.py --copy <workdir>/copy.txt --paragraphs <workdir>/paragraphs.json
```

不合格（文字对不上或超 1000 字）就修正后重跑，直到"合格"。不需要停下来等用户确认拆分，拆分结果会在最后的交付里列出。

### 4. 情绪标签，然后并发合成并拼接

**情绪标签默认要用**（用户试听对比后的结论：不加标签、只靠描述，效果不好）。规则：

- **兴奋 `[excited]` 为主，其他为辅**；一条片子用 1–3 种，不强制。只有文案里确实需要别的情绪时才用：吐槽、委屈、自嘲用 `[sad]`；轻松、调侃、道别用 `[happy]`。拿不准就用兴奋。
- **只加在整句的开头**，不加在句子中间。句中的标签会被原样念出来（出现过：句中的 `[happy]` 被念成"Happy"），也会让一句话内部变调。
- **不要太碎**：一条 1500 字的片子，自己挑的标签大约十来处，落在情绪确实转折或需要强调的句子上。
- **信息密集的地方（报档位、念清单、读提示词）也要有标签，沿用前面的情绪**，不要让这些句子突然变成没有情绪的平读。这一条脚本自动做：段首必补；段内某句没有标签、且离上一个标签已超过 80 字时补一个沿用的标签；问句标签只管问句那一句，问句后的下一句马上接回原来的情绪。每一段是单独一次合成请求，标签不会跨段生效，所以段首的沿用是必须的。
- 问句前的 `[curious]` 照旧自动加，不算情绪标签、不占 1–3 种。

做法：复制 `references/voice/emotions.example.json` 到项目目录，改名 `emotions.json`，通读文案，按上面的规则把 `tags` 填好（`at` 写那一句开头的几个字，必须是整句的开头；同样的字出现多次时用 `n` 指定第几次）。可选项：`carry` 写 `auto`（默认）、`sentence`（逐句沿用，标签最密，约每 25 字一个，没验证过效果）、`paragraph`（只段首）、`off`；`carry_gap` 默认 80；`instruction` 可以覆盖整体描述；`question_tag` 写成 `""` 则连问句标签也不加。

先看一眼实际发给接口的文字，不联网、不花钱：

```
python scripts/voice/synth.py --workdir <workdir> --dry-run
```

它会打印每段带上所有标签后的文字、标签总数、没匹配上的规则，以及不在句首的标签（有就改掉）。确认后再合成：

```
python scripts/voice/synth.py --workdir <workdir>
```

- 最多 6 路并发，提交间隔 0.5 秒：百炼对"每秒提交的请求数"限流，不是对同时在合成的数量限流，所以错开提交就能全部通过；脚本遇到 429、连接错误、5xx 会自动退避重试，只重试失败的段。
- 结果按"文字+音色+指令"缓存，重跑只补变动或失败的段。
- **标签引出来的多余语气词会自动剪掉。** 句首的情绪标签有时会让模型在句子前多“呼”出一声（嘿、哼、哎、哈……），文案里并没有。实测同一句话各合成 40 次：不加标签 0 次、`[excited]` 0 次、`[happy]` 10 次、问句的 `[curious]` 4 次。所以标签照常加，合并之前由 `scripts/voice/fillers.py` 处理：对每一段识别一次，和原文逐字比对，只找“多出来”的语气词（原文自己有的“哼！”“哦对了”不动），按音频能量找到这一声的起止，连同多出来的停顿一起剪掉（前后停顿合计留 0.5 秒内），剪完再识别一遍确认语气词没了、原文的字没少；验证不通过就保留原样并报告，不冒险。结果在合成输出里以“剪掉多余语气词 段N：X 秒处‘嘿’，已剪掉”列出，交付时要告诉用户剪了哪几处。不想剪用 `--keep-fillers`。`verify_audio.py` 会再查一遍有没有漏网的。
- 问句标签只认问号：句子以"？"结尾才会带疑问语气。通读文案时如果看到明显是问句却用了句号的句子（例如"你有没有遇到过……。"），**不要替用户改**，在交付时列出来，告诉用户"这几句改成问号后会带疑问语气"，由用户决定。
- 产物：`out/merged.wav`（段间停顿 0.3 秒、首尾已去多余静音）、`out/seg_NN.wav`、`out/timeline.json`（每段起止秒和首部裁剪量）。
- **重新合成出了不同的结果时，上一版自动存到 `out_prev/<时间>/`**，用户常常要对着听，不用自己备份。想另出一版又不覆盖：`--variant 名字`，结果写到 `out_名字/`，后面的对齐和核对加 `--out out_名字`。
- 退出码 5：`merged.wav` 被别的程序占用（多半是用户正开着播放器），新的已另存为 `merged_新.wav`。让用户关掉播放器，再重跑同一条命令，几秒钟（都已缓存）。
- 网络偶尔断线，脚本自动退避重试，有时会多等几分钟，不是出错。
- 退出码 4 表示密钥被拒绝：把 `references/voice/onboarding.md` 里"重新获取"的话告诉用户，回到第 0 步。
- 有段失败时不会拼接；把失败原因原样告诉用户。

### 5. 逐词对齐与核对

```
python scripts/voice/align_words.py --workdir <workdir>
python scripts/voice/verify_audio.py --workdir <workdir>
```

- `align_words.py`：对每段并发调用百炼语音识别，得到逐词起止时间，写入 `out/words.json`（时间在 `merged.wav` 的时间轴上，单位秒）；同时用音频能量找出停顿（≥0.25 秒），供后续分段和动作编排使用。
- `verify_audio.py`：把识别出的文字和原文比较（去标点、统一数字写法后），并统计各段语速和音高是否一致；**还会查有没有情绪标签被念出来**（识别文字里 Happy、Excited 这类词比原文多）。文字相似度发现不了这个，所以单独查。报出来就去掉那一处标签，只重合成那一段。
- 识别返回的是"词"级时间，不是字级；词与词首尾相接，所以停顿是用音频能量检测的，不要从词的间隙里找。
- 识别结果偶有同音字出入，相似度低于 0.9 的段落会标出，请用户听那一段。
- 品牌词（如 OLDX）每次、每段的读法都可能不一样，识别结果会写成 Odex、Old X 等；这是读法不稳，不是漏读。交付时提一句，让用户听。

### 6. 小结并进入下一阶段

一条龙流程里这一步不是终点：用下面的要点向用户报一句进度，然后进入数字人阶段。**例外**：用户在开头选了"配音做完先让我听"，或者只要配音，就在这里停下，等他说可以再往下做——配音一改，已经生成的人物视频就作废（要重新花钱）。

先给结论，再给依据，用中文：

- 一句话结论：配音已生成，几段、合计几秒，文件在哪，项目目录在哪。
- 列出拆段结果：每段的字数、起止秒和开头几个字。
- 核对结果：文字是否一致、各段语速音高有没有被标出（列一张各段的时长、语速、音高表，最慢和最快的段点出来）。
- 情绪标签：用了哪几种、几处，有没有被念出来。
- 问句：有几句加了疑问语气；有没有像问句但没用问号的句子。
- **没验证的**如实写：没听过音频就说明只做了数据核对，请用户试听。
- 提醒：Key 如果在聊天里出现过，建议重新生成一个。

## 失败时怎么办

| 现象 | 做法 |
|---|---|
| 退出码 3 | 没有 Key，走第 0 步 |
| 退出码 4 / 401 / 403 | Key 无效或被拒，让用户重新获取 |
| 某段重试 6 次仍失败 | 报告原始错误；其余段已缓存，修好后重跑只补这一段 |
| 接口说文字过长 | 脚本只在该段内按句号对半拆，并在交付里说明 |
| 找不到 ffmpeg、缺某个 Python 包 | 运行 `python scripts/setup_env.py --stage voice` 自动装上，再重试 |
| 识别没有返回逐词时间 | 报告原始返回，不用估算冒充；让用户知道逐词时间缺失 |

接口细节、哪些结论已验证、哪些没验证，见 `references/voice/api-notes.md`。`out/words.json` 和 `meta.json` 是给后续数字人环节用的：分段只能在 `pauses` 里断开，动作编排按 `words` 的时间对齐。
